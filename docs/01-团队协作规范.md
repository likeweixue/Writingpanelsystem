## 1. 角色与职责

### 1.1 角色定义

| 角色 | 现任 | 核心职责 | 权力边界 |
|------|------|---------|---------|
| **Owner**（产品与代码最终责任人） | 麻昌生 | 定需求优先级；对 `main` 分支与用户数据安全负最终责任；裁决技术分歧 | 可否决任何合并；可跳过 review（仅限 P0 且必须留记录） |
| **Reviewer** | likeweixue（缺省时由 Owner 兼任） | 按第 6 章清单审 PR；重点查脚本顺序 / 数据兼容 / 打包差异 | 可 Request changes；不可自行合并他人 PR |
| **Release Manager** | 麻昌生 | 版本号同步、打 tag、触发打包、验证双平台安装包、更新 Releases 说明 | 唯一可打 `v*` tag 的人 |

### 1.2 1–3 人团队的角色落位

| 团队人数 | 落位方式 |
|---------|---------|
| 1 人（当前常态） | Owner + Release Manager 由麻昌生一人承担；Reviewer 走下方"单人简化路径" |
| 2 人 | 麻昌生 = Owner + Release Manager；likeweixue = Reviewer（互相 review） |
| 3 人 | 第三人固定承担 Reviewer，Owner 专注产品与发布 |

### 1.3 单人开发时的自我 review 简化路径

> **前提**：不因为"没人审"就跳过 review，而是把 review 换成低成本形式。

| 步骤 | 做法 | 成本 |
|------|------|------|
| ① 隔夜自审 | 改动完成后**不立即合并**，次日重读 diff 一遍再合 | 0 |
| ② checklist 自测 | 对照第 6.3 节"review 关注点"逐项打勾，结果贴进 PR 描述 | 5 分钟 |
| ③ 高危改动必须找人 | 命中第 6.1 节强制 review 清单第 1–6 项的，发给 likeweixue 看一眼，或至少隔 24 小时再合 | 被动等待 |
| ④ 高危 + 无人可用 | 在 PR 描述里写明"单人合并，风险自担 + 回滚方案"，并**先 `git tag` 一个回滚点** | 2 分钟 |

## 2. 工作节奏

### 2.1 迭代周期：**双周（14 天）**

| 项 | 安排 | 理由 |
|----|------|------|
| 周期 | 14 天 | 主力只有 1 人，且每次发版要验证 Windows + macOS 两个安装包；一周太赶，一个月太久，用户反馈沉没 |
| 结构 | 第 1–10 天开发；第 11–12 天打包 + 双平台冒烟；第 13–14 天缓冲与发布 | 把"打包验证"显式排进周期，避免又出现"打包后才暴露的问题" |
| 降级规则 | 若某周期只有单人且改动 ≤ 3 个文件，可降级为周级发布 | 避免为流程而流程 |
| 热修 | P0 不受周期约束，走 `hotfix/` 分支当天发 | 用户数据丢失类问题不能等 |

### 2.2 例行仪式（**只有 3 条，不做第四条**）

| 频率 | 仪式 | 产出 | 时长 |
|------|------|------|------|
| 每周一 | **本周三件事**：在 GitHub 上给本期要做的 Issue 打上同一个 Milestone，不写额外文档 | Milestone 里有排好序的 Issue | 10 分钟 |
| 每个 PR | **合并前自检**：跑第 6.3 节检查项 + `npm start` 冒烟；命中打包敏感改动则补一次 `npm run build-win`（或 mac）并启动安装包 | PR 描述里的自检勾选 | 随 PR |
| 迭代末 | **发布与收尾**：确认版本号三处同步 → 打 tag → 触发打包 → 删除已合并分支 → 清临时文件 | 一个新 Release + 干净的分支列表 | 20 分钟 |

> **明确不做**：不开每日站会、不写周报/日报、不用看板工具、不要求 Issue 估算工时。

## 3. 需求与任务管理

### 3.1 Issue 标签体系

一个 Issue 必须同时具备 **type + priority + area** 三类标签，platform 与 special 按需。

| 类别 | 标签 | 说明 |
|------|------|------|
| **type** | `type:bug` | 已发生的功能缺陷 |
| | `type:feature` | 新功能 / 新工具 |
| | `type:refactor` | 不改外部行为的重构（抽公共模块、拆大文件） |
| | `type:docs` | 文档、README |
| | `type:chore` | 依赖升级、版本号、清理临时文件 |
| | `type:question` | 需求待澄清，不排期 |
| **priority** | `P0` / `P1` / `P2` / `P3` | 见 3.3 定义 |
| **area** | 业务模块：`area:books`、`area:editor`、`area:outline`、`area:characters`、`area:setting`、`area:settings`、`area:timeline`、`area:relation`、`area:whiteboard`、`area:namegen`、`area:notes`、`area:dictionary`、`area:dialogue`、`area:jianghu`、`area:xuefu`、`area:stats`<br>公共/基础设施：**`area:panel-window`**（被 9 个工具模块共用的全屏面板与主题色模块，改动影响面最大）、`area:ui`、`area:data`、`area:links`、`area:contextmenu`、`area:app`<br>非模块类：`area:theme`、`area:toolbar`、`area:sidebar`、`area:packaging`、`area:index-html` | 对应 `js/` 下模块或功能域；`area:index-html` 专用于 `index.html` 内联脚本与 `<script>` 顺序问题 |
| **platform** | `platform:windows`、`platform:macos`、`platform:both` | 涉及平台差异时打 |
| **special** | `risk:data-loss` | **触碰用户 localStorage 数据**，强制 review + 必须有回滚/迁移方案 |
| | `bug:package-only` | 只在打包后出现、`npm start` 复现不了 |
| | `needs-decision` | 等麻昌生拍板，不排期 |
| | `good-first-issue` | 适合协作者上手 |

### 3.2 Issue 描述模板（复制文字，不建模板文件）

```
【现象 / 期望】
- 现在：……
- 期望：……

【复现步骤】（bug 必填）
1. 打开 ……
2. 点击 ……
3. 实际结果 / 期望结果

【环境】
- 系统：Windows 11 / macOS 14
- 运行方式：npm start / 安装包（版本号：）
- 应用版本：package.json 中的 version

【影响面】
- 涉及模块：js/xxx.js
- 是否涉及 localStorage 数据结构变更：是 / 否（是 → 必须写迁移方案）
- 是否只在打包后出现：是 / 否

【验收标准】
- [ ] 在 npm start 下验证通过
- [ ] 在安装包下验证通过（打包敏感项必选）
- [ ] 旧版本用户数据升级后不丢失
```

### 3.3 优先级定义

| 级别 | 定义 | 响应 | 举例 |
|------|------|------|------|
| **P0** | 用户数据丢失 / 崩溃 / 主流程不可用，且已发布版本受影响 | 当天修，走 `hotfix/`，可跳过周期 | 升级后 localStorage 章节数据读不出来 |
| **P1** | 主要功能缺陷或高呼声需求，影响多数用户 | 本迭代内 | 打包后全屏面板打不开 |
| **P2** | 体验优化、次要缺陷、技术债 | 下个迭代 | 抽取重复主题色表 |
| **P3** | 锦上添花、长期重构 | 有空再做，不占迭代 | 拆分 `books.js` |

> **排序原则**：`risk:data-loss` 类 Issue 优先级**自动 +1 级**（最低不低于 P1）。

## 4. 分支与命名约定

### 4.1 长期分支

| 分支 | 用途 | 保护 |
|------|------|------|
| `main` | **唯一发布来源**，始终可打包可运行 | 禁止直接 push；只能经 PR 合并；打 tag 只从 `main` 打 |

### 4.2 分支命名规则

格式：`<type>/<简短英文标识>`，可选后缀 `-<issue号>`

| type | 用于 | 示例 |
|------|------|------|
| `feature/` | 新功能、新工具 | `feature/dictionary-csv-import`、`feature/outline-drag-sort` |
| `fix/` | 缺陷修复 | `fix/panel-window-blank-open`、`fix/version-string-sync` |
| `hotfix/` | 已发布版本的 P0 紧急修复 | `hotfix/data-loss-on-upgrade` |
| `refactor/` | 不改行为的重构 | `refactor/extract-panel-window`、`refactor/split-books-module` |
| `chore/` | 依赖、版本号、清理 | `chore/bump-electron-28-3`、`chore/remove-temp-files` |
| `docs/` | 文档 | `docs/team-collab-spec` |
| `release/` | 版本发布准备 | `release/v1.12.1` |

规则：
- 标识用**小写英文 + 连字符**，禁止中文、空格、大写；长度 ≤ 30 字符。
- 能从分支名一眼看出改的是哪个模块（模块名用 `js/` 下的文件主名）。

### 4.3 分支来源与合并去向

| 分支类型 | 来源 | 合并去向 | 合并后 |
|---------|------|---------|--------|
| `feature/` `refactor/` `docs/` `chore/` | `main` | → `main`（PR） | 立即删除 |
| `fix/` | `main` | → `main`（PR） | 立即删除 |
| `hotfix/` | `main`（或出问题的 tag） | → `main`（PR），并**回补**到上一个 release 分支 | 发布后删除 |
| `release/vX.Y.Z` | `main` | 不再合并回去；在此分支上做版本号同步后**打 tag** | 保留至下个版本发布 |

### 4.4 提交粒度要求

| 规则 | 要求 |
|------|------|
| 一分支一目标 | 一个分支只解决一个 Issue；顺手看到的问题另开 `fix/` 分支 |
| 单 PR 规模 | 目标 **< 400 行改动**；超过必须拆成多个 PR（例如"抽取公共模块"和"各模块接入"分开提） |
| 禁止夹带 | `fix/` 分支里不得夹带 `refactor`/`style` 改动；`refactor/` 分支里不得改行为 |
| 提交节奏 | 每天至少 1 次提交到本地分支并 push，避免本地积压导致大冲突 |
| 冲突处理 | 大文件（`books.js`/`toolbar.js`/`outline.js`）冲突时，**由改动较少的一方 rebase**，不得直接覆盖 |

## 5. 提交信息规范（Conventional Commits）

### 5.1 格式

```
<type>(<scope>): <subject>

[可选正文：说明为什么这么改 / 影响面 / 迁移方案]
[可选脚注：Refs #12 / BREAKING CHANGE: ...]
```

- `subject` 用中文，**≤ 50 字**，动词开头，不加句号。
- `scope` 填被改动的主模块（见下表）。
- 破坏性变更（**主要是 localStorage 键名/结构变更**）在 `type` 后加 `!`，正文写 `BREAKING CHANGE:`。

### 5.2 type 清单（本项目常用）

| type | 何时用 | 典型场景 |
|------|--------|---------|
| `feat` | 新增可见功能 | 词典支持 CSV 导入 |
| `fix` | 修复缺陷 | 打包后弹窗打不开 |
| `refactor` | 不改外部行为的重构 | 抽公共模块、拆大文件 |
| `style` | 样式/CSS 调整，不改逻辑 | 主题色微调、布局间距 |
| `docs` | 文档 | README、docs/*.md |
| `chore` | 依赖、版本号、清理、配置 | 升级 electron、删临时文件、发版 |
| `perf` | 性能优化 | 大章节渲染卡顿 |
| `revert` | 回滚某次提交 | `revert: "refactor(books): ..."` |
| `build` | 打包/构建相关（package.json 的 build 段、CI） | 调整 electron-builder 配置 |
| `test` | 测试相关（当前无测试，预留） | — |

**scope 取值**：`js/` 下的模块主名（`books`、`toolbar`、`outline`、`characters`、`setting`、`settings`、`timeline`、`relation`、`whiteboard`、`namegen`、`notes`、`dictionary`、`dialogue`、`jianghu`、`xuefu`、`stats`、`ui`、`data`、`links`、`contextmenu`、**`panel-window`**、`app`、`main`、`preload`），或改动载体（`index.html`、`css`、`theme`、`packaging`、`deps`、`docs`）。

### 5.3 正例（本项目真实场景）

| # | 提交信息 | 说明 |
|---|---------|------|
| 1 | `fix(panel-window): 打包后面板打不开，改为写临时 file:// 再 window.open` | 说清问题现象 + 手段 |
| 2 | `refactor(panel-window): 抽取 9 个模块重复的主题色表与弹窗逻辑` | 正文补 `-153 行，9 处调用点` |
| 3 | `fix(main): 关于对话框版本改为读取 package.json，不再硬编码 1.9.1` | 版本号真源治理 |
| 4 | `feat(dictionary): 词条支持 CSV 批量导入` | 功能清晰 |
| 5 | `chore(deps): electron 28.0.0 → 28.3.3，electron-builder 24.6.4 → 24.13.3` | 升级写全版本号区间 |
| 6 | `revert: "refactor(books): 拆分书籍管理模块（打包后章节列表异常）"` | revert 必须带原因 |
| 7 | `refactor(data)!: 大纲存储键改为 openwrite_outline_v2` + 正文 `BREAKING CHANGE: 需从 v1 键迁移` | 破坏性标 `!` |

### 5.4 反例（禁止出现）

| # | 反例 | 问题 |
|---|------|------|
| 1 | `修改了一些东西` | 无 type、无信息 |
| 2 | `fix bug` | 无 scope、无内容 |
| 3 | `更新` / `update` / `提交` | 完全无意义 |
| 4 | `feat: 新增九大工具 + 修复打包问题 + 改主题色` | 一个提交三件事，必须拆 |
| 5 | `Fix(PanelWindow): ...` | type 必须小写；scope 应为 `panel-window` |
| 6 | `fix(books): 修复问题（原因后面再说）` | subject 不能含糊 |

> **建议采纳的检查项（不落地配置文件）**：人工自查即可，或在本地配一条 commit-msg 检查：
> `grep -Eq '^(feat|fix|refactor|style|docs|chore|perf|revert|build|test)(\(.+\))?!?: .+' .git/COMMIT_EDITMSG`

## 6. Code Review 规则

### 6.1 强制 review 场景（命中任意一条，必须有人审过才能合并）

| # | 场景 | 原因 |
|---|------|------|
| 1 | 改动 `index.html` 的 `<script src>` 顺序或增删 `js/*.js` 引入；**以及改动 `index.html` 中的任何内联 `<script>`**（含 178–382 行与 `</html>` 之后的 413–479 行"永久修复"补丁） | 脚本顺序即依赖，错序直接白屏；内联补丁会造成按钮重复绑定与互相覆盖 |
| 2 | 改动 `main.js` / `preload.js` | 主进程、IPC、窗口、`setWindowOpenHandler` 白名单 |

## 7. 重复代码与文件治理

### 7.1 「三振出局」规则

> **同一段逻辑（或同一份数据表）出现第 3 次时，必须抽取到公共模块，不允许第 4 次复制。**

| 出现次数 | 动作 |
|---------|------|
| 第 1 次 | 就地写，不管 |
| 第 2 次 | 允许复制，但**必须在文件头注释写** `// TODO: 与 js/xxx.js 重复，第三次出现时抽取` |
| 第 3 次 | **必须抽取**：新建 `js/<公共模块名>.js` → 在 `index.html` 中排到所有调用方之前 → 3 处调用改为引用 → 单独提一个 `refactor/` PR（只做抽取，不改行为） |

**本项目已发生的真实案例（作为范式）**：

| 项 | 内容 |
|----|------|
| 重复物 | 5 套主题色表 `themeColors` + `window.open('', '_blank') + document.write(html)` 弹窗代码 |
| 重复次数 | 9 个工具模块各一份（outline/characters/notes/setting/dictionary/relation/namegen/timeline/whiteboard） |
| 抽取结果 | `js/panel-window.js`，提供 `getPanelTheme()` / `openPanelWindow()`，共精简 **153 行** |
| 附带收益 | 顺带修掉"Electron 打包后空 URL 被 `setWindowOpenHandler` deny 导致弹窗打不开"的打包态缺陷 |

**建议采纳的检查命令**（不落地配置，需要时手跑）：

```bash
# 找重复的主题色定义
grep -rn "themeColors\|#1a1a2e" js/ | head -20
# 找重复的弹窗写法
grep -rn "window.open(" js/ | head -20
```

### 7.2 临时文件规范

| 规则 | 要求 |
|------|------|
| 命名 | 调试文件**必须**带 `temp_` / `tmp_` / `debug_` 前缀，便于一眼识别 |
| 存放位置 | 优先放**仓库外**（如 `/tmp`）；必须放仓库内的，当天删 |
| 禁止提交 | 0 字节文件、只用于一次性数据修复的 `*_fix.js`、个人调试脚本 |
| 提交前必查 | `git status --porcelain` 逐行确认无临时文件 |
| 已存在的历史债 | `js/temp_books.js`（0 字节）、`js/temp_switchpage.js`、`js/openbook_fix.js` → 在下一个 `chore/` PR 中清理（`js/openbook_fix.js` 需先确认功能是否已并入 `books.js`，**确认后再删**） |
| 一次性修复残留（内联补丁） | `index.html:413–479` 名为"永久修复"的内联补丁，位于 `</html>` **之后**，用 `.onclick=` 再次绑定 `newBookBtn`/`newGroupBtn`/`confirmNewBookBtnV2`/`confirmNewGroupBtnV2`；另有 `index.html:380–381` 的调试 `console.log` → 单开 `chore/` 或 `fix/` PR 移入 `js/app.js` 或删除。**动手前必须先核对冲突方**：同一批按钮在 `index.html:360–363` 已绑定过一次，且 `js/app.js:149–150` 还把它们绑到了旧抽屉 `openDrawer('newBookDrawer')`（注意：不是 `js/books.js`，books.js 中无任何相关绑定）。三处并存，直接用 `.onclick=` 覆盖生效顺序取决于加载先后，**必须先确定唯一绑定来源再删**，否则会删掉真正生效的那一个 |

### 7.3 单文件拆分触发线

| 阈值 | 动作 |
|------|------|
| > 60KB 或 > 1500 行 | **触发拆分评估**：在相关 Issue 上登记，不强制本次改 |
| > 100KB | **必须拆**：下一次触碰该功能的 PR 里完成拆分（`refactor/` 类型，先拆不改行为） |
| 拆分方式 | 按功能子域拆成 `js/<模块>-<子域>.js`，并在 `index.html` 中按依赖顺序插入；同时更新 README 项目结构 |

### 7.4 命名约定

| 规则 | 说明 |

## 8. 版本号唯一真源

> **硬规则：`package.json` 的 `version` 字段是本项目版本号的唯一真源。**
> README 徽章、`main.js`「关于」对话框必须与它**完全一致**，且必须在**同一个 PR** 内同步完成。不同步的 PR 一律不予合并。

### 8.1 当前不一致事实（必须修）

| 位置 | 当前值 | 应改为 |
|------|-------|-------|
| `package.json:3` | `"version": "v 1.12.0"` | `"1.12.0"`（**去掉 `v` 前缀和空格，当前不是合法 semver**，`npm version` / electron-builder / CI 都可能出错） |
| `README.md:6` 徽章 | `release-v1.9.1` | `release-v1.12.0` |
| `main.js:276` 关于对话框 | `版本 1.9.1` | 改为**读取** `package.json` 的 version，不再硬编码 |

### 8.2 版本号规则

| 规则 | 要求 |
|------|------|
| 格式 | 严格 semver `MAJOR.MINOR.PATCH`（如 `1.12.0`），**字段值内不得含 `v` 或空格** |
| tag 格式 | `v1.12.0`（tag 带 `v`，字段不带，这是唯一允许的差异） |
| 递增约定 | P0/P1 缺陷修复 → PATCH；新增功能 → MINOR；不兼容的数据/行为变更 → MAJOR |
| 真源读取 | `main.js` 通过 `require('./package.json').version`（或经 `preload.js` 暴露给渲染进程）取版本号，**杜绝硬编码** |

### 8.3 发版前同步清单（Release Manager 逐项打勾）

- [ ] `package.json` 的 `version` 已改为合法 semver（无 `v`、无空格）
- [ ] `README.md:6` 的 release 徽章版本号已同步
- [ ] `main.js` 关于对话框显示的版本号来自 `package.json`（非硬编码）
- [ ] 提交信息：`chore(release): v1.12.0`
- [ ] 从 `main` 打 tag：`git tag -a v1.12.0 -m "v1.12.0"` → `git push origin v1.12.0`（触发 `.github/workflows/build.yml` 双平台打包）
- [ ] 下载两个 artifact 各启动一次冒烟（重点：弹窗窗口、导入导出、主题切换）
- [ ] GitHub Releases 写好更新说明（新增 / 修复 / 已知问题）
